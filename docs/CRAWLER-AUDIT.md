# Crawler audit — 16 October 2026

Status: initial audit retained for reference. Implementation and validation are documented in [ACCURACY-UPDATE.md](ACCURACY-UPDATE.md).

## Evidence collected

- Started `pnpm start:local`; embedded PostgreSQL, web dashboard and worker started successfully. The normal scheduler automatically started a catch-up crawl. No extra manual crawl or Telegram test message was triggered.
- Inspected the home, collection-history and notifications pages in the browser, plus existing data through a read-only database transaction.
- Live crawl extracted 72 cards from `/ventes-flash` over HTTP, 60 from `/destockage` through the browser, 36 from the autumn deals page, 180 from the under-200-DH page, and 142 from the filtered men's T-shirt page. These counts are extraction output, not independently verified catalogue totals.
- `/destockage/mode-sport` and `/destockage/high-tech` failed with `fetch failed`. The filtered hoodies page produced zero cards even after browser rendering.
- Telegram startup failed at `getMe` with `Telegram injoignable : fetch failed`. This does not prove an invalid token. The process exits instead of retrying initialization.
- `pnpm test`: 95 passed, 24 skipped. PostgreSQL integration tests were skipped because `TEST_DATABASE_URL` was absent. The application's real database was not used as a destructive test database.
- Workspace type checking passed in the preceding inspection.
- Small isolated reproductions are saved in `.audit/reproduce.ts`; application startup output is in `.audit/app.stdout.log` and `.audit/app.stderr.log`.

## Fix list

P1 = high priority correctness/reliability; P2 = next reliability/performance work. “Code-confirmed” means the faulty path was traced, but its full production consequence was not reproduced against the live site.

| ID | Priority / evidence | Problem and proposed fix | Acceptance check |
|---|---|---|---|
| F01 | P1 — reproduced | **URL filters are not enforced.** `adapter.ts:73–80` accepts any server products and skips rendering, although size/gender URL facets are client-side. An isolated size-42 request returned a size-41 item through HTTP. The real crawl also used HTTP for a filtered sports listing. Use a filter-aware acquisition path and verify the selected facets; preserve evidence of which filters were actually applied. | A size-41 item cannot qualify for a size-42 search. If size cannot be verified, show unknown and exclude it from strict matching. |
| F02 | P1 — UI + reproduced | **Brand words become product types.** `evaluate.ts:74–98` matches keywords against brand + title and relaxes category checks for promo-only offers. `Sneakers PEPE JEANS taille 41` passes a trousers search with keyword `jean`; actual PEPE JEANS sneakers appear under trousers on the dashboard. Use product type/category evidence and distinguish brand terms from garment terms. | PEPE JEANS sneakers fail trousers searches; actual jeans still pass. Promo origin alone cannot override a required product type. |
| F03 | P1 — data + code | **Search names promise sizes the stored rules do not prove.** The active trousers search is named 32/33, but its stored path contains only gender and no size/spec rule. Other size searches rely on F01's URL behavior. Represent sizes as explicit typed constraints; audit existing criteria and show unverifiable sizes clearly. | Every size-labelled search has an enforceable size condition. Unknown size never appears as verified 32/33, M, or 42. |
| F04 | P1 — code-confirmed | **Incomplete listing coverage can mark valid offers missing.** HTTP discovery returns after one page even when `maxPages=4`; `applyMissingPolicy` treats any nonempty listing as successfully crawled. Browser discovery reports the requested page count even if it stopped early. Track actual batches, completeness and stop reason; only use sufficient coverage to infer absence, or verify the product directly. | An item moving beyond the first page remains active. Truncated/failed pagination cannot increase absence counters. Metrics report actual pages loaded. |
| F05 | P1 — live + UI | **Telegram startup and readiness are unreliable.** A transient startup network error exits the bot (`apps/worker/src/bot.ts:166–171`). The dashboard tests token + legacy chat ID and shows setup instructions even though the subscriber bot uses token-only enrollment. Add retry/backoff and a bot heartbeat; render configured, connecting, healthy and failed states. | Starting offline and restoring connectivity recovers without restarting the stack. Token + active subscriber is correctly represented in the UI. |
| F06 | P1 — code-confirmed | **Alert delivery does not honor every global switch.** The subscriber delivery loop checks notification settings but does not check `appSettings.notificationsEnabled`, unlike the worker's legacy delivery path. Unify delivery policy checks. | Turning the global notification switch off prevents both subscriber and legacy delivery. |
| F07 | P1 — reproduced key collision | **Fashion variants can share a product record.** `canonicalProductKey` includes screen/RAM/storage, but ignores clothing size, shoe size and colour. Two different source offers with the same brand/model produce the same key. Keep uncertain fashion variants separate until variant identity is proven. | Same model in different sizes/colours retains independent metadata and variant identity; valid seller comparisons still work. |
| F08 | P1 — code-confirmed | **A poorer observation can discard rich product identity.** `persist.ts:56` recomputes the product key from the latest observation, then moves the offer and can delete the old orphan product. A listing missing previously known specs/ref can move it back to a placeholder, losing rich specs despite the preservation comment. Resolve against the existing product before choosing identity. | Detail observation followed by a sparse listing preserves product identity, specs and comparison grouping. |
| F09 | P1 — code-confirmed | **A confirmed 404 can still become an active listing offer.** In the candidate loop, a `gone` detail response is logged and the listing fallback is persisted as active; the tracked-offer loop correctly marks it unavailable. Give authoritative product 404/410 precedence consistently. | Candidate + stale listing + product 404 becomes unavailable and cannot generate a new-match alert. |
| F10 | P2 — live + code | **Extraction failure can look like successful coverage.** Zero-card pages are recorded as informational notes, including the live rendered hoodies page. After one browser failure, later browser-needed pages return empty results without individual failure evidence. Distinguish verified empty catalogue from extraction failure, timeout and browser-disabled outcomes. | A broken selector/browser produces a partial or failed coverage status with a specific reason; a verified empty catalogue remains a valid empty result. |
| F11 | P2 — code-confirmed | **Browser pacing ignores its configured delay.** `RenderOptions.minDelayMs` is passed but unused; pagination uses fixed 400/1200-ms waits and HTTP/browser navigation do not share a request schedule. Use a shared budget for navigations and explicit pagination requests; wait for data changes instead of fixed sleeps. | Configured delay is respected for controlled crawl requests; slow-loading batches do not terminate pagination prematurely. |
| F12 | P2 — code-confirmed | **Redirect validation happens after the request.** `http.ts` follows redirects automatically and only checks the final URL afterward. Validate each redirect destination before following it; apply equivalent navigation rules to browser rendering. | A redirect to a disallowed host is rejected before that host receives a request. |
| F13 | P2 — code-confirmed | **Long histories cause growing per-offer work.** Every observation reloads and sorts the full price history, then evaluates each criterion with separate queries inside a transaction. Replace full-history reads with bounded previous/min/count aggregates and batch relevant reads. | Scores/history facts remain equivalent while query cost stays bounded as history grows. |
| F14 | P2 — validation gap | **The live diagnostic and tests do not cover the real acquisition path.** `probe` uses the DOM parser rather than production's embedded-data merge and discovery logic. Database tests were skipped. Exercise production discovery in diagnostics, add sanitized real-page regression fixtures, and run DB tests against a dedicated disposable database. | Probe and worker agree on the same fixture; CI executes pagination, identity, missing-policy, 404 and delivery-policy regression cases. |
| F15 | P1 — live failure, root cause pending | **Product detail prices fail extraction.** The live catch-up crawl logged `Prix introuvable ou invalide` for the cargo trousers and two PEPE JEANS shoe pages. Capture representative responses and compare the product parser with structured/embedded price data and the visible selected variant. Fix the responsible parser or response classification after that comparison. | Real-page fixtures yield the correct selected-variant price, or an explicit blocked/unavailable/unknown result; a failed detail extraction cannot masquerade as a verified detail price. |

## Additional operational follow-up

- The local web command binds to all interfaces while auth bypass trusts a localhost Host header. Bind local mode explicitly to loopback; verify with a listener check. This was observed in the startup network URL and listener output and should be addressed before network exposure.
- Notification fan-out stores one delivery state for all subscribers. A transient failure for one subscriber can resend to subscribers who already received the alert. Add per-recipient delivery state before relying on multiple subscribers.
- Retain useful network error causes (DNS, TLS, timeout, proxy) without logging tokens. Current `fetch failed` messages do not diagnose the observed listing/Telegram failures.
- Reconcile documentation with actual behavior: pagination, filtered paths, current default detail budget, browser behavior, and subscriber enrollment.
- Review the browser's automation-fingerprint overrides and remove unnecessary concealment settings; do not treat them as a substitute for permission or reliable access.

## Suggested implementation order

1. F01–F03: search accuracy and explicit size evidence.
2. F04, F07–F10, F15: coverage, identity, price extraction and lifecycle correctness.
3. F05–F06: Telegram recovery, policy and truthful readiness.
4. F11–F14: pacing, redirect checks, scale and validation.

These were the original proposed checks. The subsequent implementation uses strict required attributes and conservative absence inference; see [the update notes](ACCURACY-UPDATE.md) for completed work and remaining limits.
